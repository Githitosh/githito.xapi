# githito.xapi

ニュースのページ（https://githitosh.github.io/news-shorts/ ）とユーモアのページ（https://githitosh.github.io/news-shorts/humor/ ）のための、
**自分専用のAPI**です。このリポジトリのプログラムが、Xの投稿とリプライを**30分ごとに自分で集め続け**、ファイルに保存します。
ページはXを直接検索せず、そのファイルを読むだけです。プログラムもデータもこのリポジトリの中にあり、内容を変えられるのは持ち主だけです。

## 取り込み量のグラフ

![取り込み量（1時間ごと・直近48時間）](https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/intake.svg)

1時間ごとに新しく取り込んだ数です（上：リプライニュースの会話、下：ニュースの見出し。日本時間）。実行のたびに `stats.mjs` が描き直します。
同じものを次の3か所で見られます。

- **このページの上のグラフ**（直近48時間）。
- **Actions タブの実行の一覧**：実行の名前が、直近12時間の小さなグラフになっています
  （例：`会話 ▂█▆█▇▇█▂█▆▃▄ 613組 ・ 見出し ▂▃▃▂▂▂▂▂▃▃█▂ 1193件（直近12時間）`）。棒が低い・`▁` が続くときは、取り込めていない時間です。
- **それぞれの実行のページ（Summary）**：グラフ、その実行で増えた数、1時間ごとの表（直近24時間）、日ごとの表。

数字そのものは `v1/stats.json` にあります（7日分）。あとでルールや古さで消えた分も、取り込んだ数には入ったままです。

## 自分で動き続ける仕組み（30分ごと、止めるまでずっと）

- 定時実行（スケジュール）ではなく、**実行が終わるたびに次の実行を自分で始める**作りです（`next.mjs`）。1回の流れ：
  ユーモアの収集（最大14分）→ 公開 → ニュースの収集（最大10分）→ 公開 → 始めてから30分たつまで待つ → 次の実行を始める。
  これが30分ごとに、止めるまでずっと続きます。間隔は `config.json` の `"cycle"`（分）で変えられます。
- GitHub の定時実行は数時間遅れたり動かなかったりするため、それには頼りません。3時間おきの定時実行を1つ残していますが、
  これは連鎖が万一切れたときに始め直すためだけの保険です（連鎖が動いている間は何もしません）。
- **止めるとき**：`config.json` の `"loop"` を `false` にします（その回で終わり、次を始めません）。Actions タブでワークフローを無効にしても止まります。
- 手で実行したとき（Actions タブ →「Collect」→ Run workflow）は、待っている実行が道を譲り、終わると連鎖を続けます。
  `only` に `news` か `humor` を入れると片方だけ、`rejudge` にチェックを入れると検索せずに保存済みのデータを今のルールで判定し直すだけになります。
- **3日たったものは消えます**（ユーモアの組、ニュースへの返信、見出しのすべて）。

## 何を流すかは、ここで決めます（ランダム）

集めたあと、**再生する順番をこのリポジトリが乱数で決めて**ファイルに書きます（`pick.mjs`、各ファイルの `play`）。ページは上から順に読むだけです
（読む人がすでに見たものは飛ばします）。順番は乱数ですが、次の決まりを守ります。

- 新しいものが前に来やすい（乱数が主で、新しさは少し効くだけ）。
- 同じ人・同じニュースが近くに並ばない（1本の動画の長さの中で重ならない）。
- ニュース `play.news`：見出しだけ（ページはふだんこれを流します）。`play.replies`：頼まれたアカウントへの返信と、返信を付けないニュース（政治・治安）の見出し。`play.genre`：ジャンルごと。
- ユーモア `play.morning`：10組のうち7組が「おはよう」、3組が恋愛。`play.day`：7組が恋愛、3組が「おかえり」など。`play.night`：7組が恋愛、3組が「おやすみ」など。

## Xの読み方（複数のサービス）

1つが断られても止まらないよう、複数のサービス・複数の入口を使います。

| サービス | 使い道 |
|---|---|
| **FxTwitter**（api.fxtwitter.com） | 検索（search）、会話の読み出し（conversation：投稿・前後のやりとり・返信が1回で返る）、アカウントのタイムライン（profile/statuses）、プロフィール |
| **vxTwitter**（api.vxtwitter.com） | 投稿1件の読み取り（返信先のニュース投稿、会話が断られたときの返信先） |
| **FixupX**（fixupx.com） | 投稿1件の読み取り（vxTwitter で読めなかったとき） |
| **X公式の埋め込み**（publish.x.com） | 投稿1件の読み取り（上の2つで読めなかったとき） |

新しい投稿を「探す」ことができるのは FxTwitter の検索だけで、これは続けて使うと断られます。そのため、検索を使わない入口（会話・タイムライン）を主にし、
断られた入口は数分休ませて他を進めます。

## ユーモアページ用のデータ（`humor-ja.json`）

ユーモアのページ（https://githitosh.github.io/news-shorts/humor/ ）用の**恋愛のやりとり**（投稿と、それへの返信の2つ1組）を、
`humor.mjs` が**30分ごと**に集めて `v1/humor-ja.json` に置きます。ページはそれを読むだけなので、すぐ再生できます。

- **複数の経路**でXを読みます（1つが断られても止まりません）：
  1. **検索**（api.fxtwitter.com の search）：愛情や挨拶の言葉を含む返信を、直近の数時間から探します（1回の実行で最大60回）。
     挨拶は言われる時間帯に探します：おはようは日本時間の5〜10時、おやすみは21〜2時、おかえり・おつかれは17〜23時。
  2. **タイムライン**（api.fxtwitter.com の profile/statuses）：すでに集めた人と、読んだ会話に出てきた人の最新の投稿のうち、返信が付いたもの（検索を使いません）。
     まだ読んでいない人から順に、1回の実行で最大60人。
  3. **会話の読み出し**（api.fxtwitter.com の conversation）：1回の問い合わせで、その投稿・それより前のやりとり・下に付いた返信がまとめて返ります。
     その中の「投稿と返信」の組をすべて調べ、流せる組を残します（1つの会話から2組まで）。
  4. 会話が断られたときは、返信先の投稿を **vxTwitter**（読めなければ **FixupX**）で、書いた人のプロフィールを FxTwitter で読みます。
- 1回の実行は最大14分。断られた経路は数分休ませ、その間ほかの経路を進めます（断りは15分ほどで解けます）。**新しい組が100たまったら**そこでやめて出力します。
- 残すもの：くだけた口調の二人のやりとり（別々の人、有名人ではない）。愛情か挨拶の言葉があること（♡だけでは残しません）。
- 外すもの：暴力・性的な内容・重い話題・体に関する話、丁寧語や「さん」付けの挨拶、作品・配信・企画・絵の話、出産や子どもの話、店・公式・配信者。
  **学校に関する言葉を書いている人、プロフィールで未成年と分かる人は、その人ごと外します**（2週間）。
- 同じ人ばかりにならないよう、1人につき4組まで（1回の実行では2組まで）。3日たった組は消えます。最大1500組。
- 再生する順番はここで乱数で決めます（上の「何を流すかは、ここで決めます」）。ページは朝（4〜11時）は `play.morning`、夜（20〜4時）は `play.night`、それ以外は `play.day` を上から読みます。
- `config.json` の `humor` で設定します（`"on": false` で止まります）。`source` が `off` でも、こちらは動きます。

## ニュースページ用のデータ（`news-ja.json`）

ニュースのページ（https://githitosh.github.io/news-shorts/ ）は、Xだけを情報源にします。`news.mjs` があらかじめ次の2つを集めて
`v1/news-ja.json` に置き、ページはそれを読むだけなので、すぐ再生できます。

**ページはふだん、ニュースの見出しだけを流します（リプライなし）。** リプライは、ページの設定でアカウントを頼んだときだけ、そのアカウントの投稿に付いたものを流します。

**アカウントの頼み方（`account`）**
1. ニュースのページの設定 →「リプライとコメントを流すアカウント」にアカウントを入れて「追加」し、「xapiに送る」を押します。
   タイトル `account`、本文にアカウントが1行ずつ入った Issue の画面が開くので、Submit を押します（手で作るときも同じ形です）。
2. Issue の本文が `v1/accounts.json` の一覧になります（最大8つ。送るたびに置き換わります。本文が空か `none` なら一覧を空にします）。
   読むのは、このリポジトリの持ち主が作った Issue だけです。Issue は結果のコメント付きで閉じられます。
3. 次の実行（30分ごと）から、そのアカウントの投稿と、それに付いたリプライを集めます。ニュースのアカウントでないもの（個人など）の投稿には
   `"q": 1` が付き、ページはそのアカウントを頼んだ人にだけ流します。
4. **頼まれたアカウントがないときは、リプライを1件も探しません・読みません**（非公式のサービスに尋ねる回数が減ります）。
5. **送られたアカウントも、同じフィルターを通します。偏らせないためのルールもあります。**
   - 残酷なニュース・個人の名誉にかかわるもの・誹謗中傷は、送られたアカウントの投稿や返信でも載せません（`filters.mjs`）。
   - ニュースのアカウントでないもの（個人など）は、さらに厳しく見ます：政治、特定の集団に触れるもの、けんか腰・非難、重い話題、広告、
     Xがセンシティブと印を付けた投稿は載せません。鍵付きのアカウント、プロフィールから未成年と分かるアカウントは何も取りません。
   - 1つのアカウントが取りすぎないようにします：1回の実行で新しく入れるのは5件まで、保存しておくのは20件まで。
     送られたアカウントの返信を読むのに使う時間は、1回の実行の5分の1まで（残りはみんなのニュースに使います）。
   - 再生順では、同じアカウントが3つ以内に続けて出ないようにします（10枚の動画で、1つのアカウントは最大4枚）。これは送られたものに限らず全部に効きます。
6. **1つのところから大量に送られたら、一時的に止めます**（`limit.mjs`）。送り主（Issue を作った GitHub アカウント）ごとに数え、
   1時間に5件、または1日に20件を超えたら、その送り主からの依頼を6時間受け付けません。その間の Issue は理由を書いて閉じ、設定はそのまま残します。
   数は `v1/requests.json` に入ります。
   一覧から外したアカウントのリプライは、次の実行でファイルから消えます。

**1. 頼まれたアカウントへの真面目なリプライ（`items`）**
- 探し方（**複数の経路**。1つが断られても止まらないようにしています。どれも頼まれたアカウントの投稿だけが対象です）：
  1. **会話の読み出し**（api.fxtwitter.com の conversation）：ニュース投稿1件につき1回の問い合わせで、その投稿と返信約20件が返ります。
     返信の多い投稿から順に、1回の実行で最大250件読みます。返信先をたどる必要がないので、これが主な経路です。
  2. **返信の検索**（api.fxtwitter.com の search）：頼まれたアカウントに宛てた返信を検索します（1回の実行で最大80回、1回で約20件）。
     見つかった返信が答えているニュース投稿は、**vxTwitter → FixupX → X公式の埋め込み（publish.x.com）→ FxTwitter** の順で読みます。
  3. ニュース投稿そのもの（見出し）は、**アカウントのタイムライン**（api.fxtwitter.com の profile/statuses）で読み、返らないときは検索で読みます。
- 残す返信：12〜80文字の、ニュースについての考えを普通の言葉で書いたもの。笑い（笑・w・草）、応援や歓声、絵文字だけの反応、
  悪口・批判・決めつけ、人を指す言い方、宣伝は外します。
- 返信を付けないニュース：**政治・行政・国際情勢・皇室**（返信が人への言い合いになるため）、事件・事故・災害・訃報・病気・スキャンダル。
- **1回の実行は、流せる返信が新しく100件たまったところで問い合わせをやめて出力します**（`config.json` の `news.enough`）。残りは次の定時実行で集めます。
- 1つのニュースにつき返信は8件まで。最大2000件、72時間たったものは消えます。真面目な返信は全体の1〜2割なので、1回の実行で増えるのは数十〜200件ほどです。

**2. ニュースの見出し（`heads`）**
- ニュースアカウントの最新の投稿そのもの。政治・治安も含み、ジャンルを付けます。ページはふだんこれを流します。
- 集め方はユーモアと同じ**ラウンド方式**です：1回の実行（最大12分）のあいだ、アカウントを順に読みます。入口は2つ
  （**タイムライン**と、そのアカウントの投稿の**検索**）。片方が断られたら2分休ませてもう片方で続け、読めなかったアカウントは順番を後ろに回してもう一度試します。
  主な30アカウントは毎回、残りは「前に読んでから時間がたった順」に読むので、毎回ちがうアカウントの新しい投稿が入ります。
- **ニュースはXから集めます。ウェブのニュース検索や、日本のメディアのRSSは使いません**（ページ側も同じです）。
  その分をXで補うため、見出しだけを読むアカウントを10個足しました：ブルームバーグ、ウォール・ストリート・ジャーナル日本版、
  AFPBB News、CNN.co.jp、日経電子版 ビジネス、東京新聞、J-CASTニュース、CNET Japan、Impress Watch、ギズモード・ジャパン。
  自分で足したいメディアは、ニュースページの設定の「アカウント」にXのアカウント名を入れて送ります。
- **再生順は新しいもの優先**です（見出しの新しさ＋最大3時間ぶんの乱数）。ページは上から、まだ見ていないものを流すので、更新のたびに新しいニュースが出ます。
- 新しい順に最大1500件（ページがファイル全体を読むため）。3日たったものは消えます。
- 見出しには**英語**（`e`、Google翻訳。GitHub 上からは断られることが多く、付かなかった分はページ側が翻訳を取りにいきます）と、投稿の続きの短い1行（`d`、あれば）を付けます。
  ニュースのページは、英語の大見出し・小見出しと日本語の行を並べたカードにして流します。

共通：
- api.fxtwitter.com の検索は続けて使うと断られます（会話の読み出しとタイムラインは、検索が断られているときでも読めることを確認しています）。30分ごとの実行でためていきます（1回の実行は最大10分）。
- `config.json` の `news` で設定します（`"on": false` で止まります）。
- Actions の Run workflow で `only` に `news` と入れるとこの収集だけを動かせます。`searches` に数字を入れると、その回の返信の検索回数を変えられます。

ファイルの形：`news` はニュース（`h` アカウント、`n` 名前、`t` 見出し、`g` ジャンル）、`items` は返信（`h` 書いた人、`t` 本文、`n` ニュースの番号）、
`heads` は見出し（`h` アカウント、`n` 名前、`t` 見出し、`g` ジャンル、`id` 投稿の番号、`q` ニュースのアカウントでない頼まれたアカウントの投稿）、
`asked` は頼まれたアカウント（`h` アカウント、`n` 名前、`news` ニュースのアカウントかどうか）。

## APIの入口

ブランチ `api` に置いたファイルが、そのままAPIの応答です（GitHub が配信します。鍵は要りません）。

| 入口 | 内容 |
|---|---|
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/talks-ja.json` | その日の会話すべて（日本語、最大500件） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/search/ja/food.json` | ジャンルごとの会話（`food` の部分がジャンル） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/match-ja.json` | マッチングニュース用：単独で読める投稿（`posts`）と、どの投稿にも合う一言（`lines`） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/news-ja.json` | ニュースページ用：Xのニュースの見出し（最大1500件）と、頼まれたアカウントへの真面目な返信（最大2000件） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/accounts.json` | ニュースページの設定から頼まれたアカウント（リプライを集める相手） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/humor-ja.json` | ユーモアページ用：恋愛のやりとり（最大600組） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/stats.json` | 取り込み量：1時間ごとの新しい会話・見出しの数（7日分）と、最後の実行の数字 |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/intake.svg` | 取り込み量のグラフ（直近48時間の画像） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/index.json` | 最終更新の時刻と、ジャンルごとの件数 |

ジャンル：`space` `politics` `science` `culture` `local` `entertainment` `safety` `sports` `food`
`restaurant` `romance` `travel`（手で送った会話でどれにも当たらないものは `other`）

## いつ更新されるか

毎日 **6時・12時・18時（日本時間）** に、`.github/workflows/collect.yml` が `collect.mjs` を動かします（ユーモア用の `humor.mjs` はこれに加えて毎時17分にも動きます。GitHub の定時実行は混雑時に大きく遅れるため、ちょうどの時刻を避けて7分・17分にしています）。
1回の実行で、恋愛の投稿を約1000件、リプライを約1000件（合わせて約2000件）集め、下の3段階のフィルターにかけます。
残った会話は新しいものから500件を残します（48時間たったものは消えます）。
GitHub の都合で、開始が数分〜十数分遅れることがあります。
Actions タブ →「Collect」→ Run workflow で、すぐ1回動かすこともできます。
そのとき `rejudge` にチェックを入れると、検索は一切せず、保存済みのデータを今のルールで判定し直すだけの実行になります
（ルールを直したあと、すぐAPIから外したいときに使います。30秒ほどで終わります）。

## 載せないもの（必ず外す）

ページ側のスイッチに関係なく、次のものは集めた時点で外します（`filters.mjs`）。保存済みのデータも、実行のたびに同じルールで見直します。
ニュースのページとリプライニュースのページも、同じリストでもう一度確かめてから流します（news-shorts の `src/never.js`。変えるときは両方）。

| リスト | 外すもの | どこに効くか |
|---|---|---|
| `CRUEL` 残酷なニュース | 殺害・殺人、遺体、拷問・処刑、性暴力、虐待・暴行、自殺、子どもが被害にあった事件、攻撃で死者が出た話 など | ニュースの見出し |
| `PERSONAL` 個人の名誉・私生活にかかわるニュース | 逮捕・容疑者・起訴・判決（懲役など）、疑惑・告発・暴露・スキャンダル、不倫・熱愛、ハラスメントやいじめの告発、炎上・バッシング など | ニュースの見出し |
| `SLANDER` 人が書いた言葉の中の誹謗中傷 | 悪口・侮辱・差別語、「死ね」などの脅し、人を犯罪者・嘘つき・詐欺師などと決めつける言葉、住所・本名・勤務先などを指す言葉 | ニュースへの返信、リプライニュースの会話 |

- 報道機関が逮捕や疑惑を報じること自体は正当ですが、短い動画のページが個人名つきで繰り返すと、その人への中傷になりかねないので載せません。
- 言葉の一部が無害な語に当たる場合は除いています（例：「殺到」「くぎを刺された」「通信ケーブル切断」「整形外科」「性的少数者」は外しません）。
- 言葉で判定しているので、完全ではありません。漏れや外しすぎを見つけたら、`filters.mjs` の語を足し引きします。

## 3段階のフィルター

集めた約2000件は、次の順にふるいにかけます。各段階を何件が通ったかは、実行のログと `index.json` の `stages`（`match-ja.json` にも同じもの）に残ります。

| 段階 | 何を見るか |
|---|---|
| 集める | 検索で返ってきた投稿・リプライ（1回の検索で20件ほど。投稿50回＋リプライ50回） |
| フィルター1：出してよいか・誰のアカウントか | 暴力・性的な内容・重い話題・けんか腰・広告・勧誘・体に関する話・学校に関する言葉を外す。投稿は、作って1年以上・投稿300件以上・フォロワー30〜5万人のアカウントだけ。プロフィールに勧誘や販売があるもの、鍵付き、未成年と分かるものは外す |
| フィルター2：内容が合っているか | 投稿は「単独で読める、本人の恋愛の話」だけ（作品・キャラクター・芸能人・結婚生活・説教調は外す）。リプライは「ツッコミや笑いのある返信」か「数文字の反応」だけ |
| フィルター3：X公式で読み直して再判定 | 通ったものを X公式の埋め込みAPIで読み直し、X の本文でフィルター1・2をもう一度かける。リプライは、返信先の投稿も読んで判定する。X で表示されないものは捨てる |

このあとページ側で、組み合わせるときにもう一度選びます（別の人どうし、本当の返信ペアではない、リプライが触れている言葉が投稿にある）。

## マッチングニュース用のデータ（`match-ja.json`）

ページの「マッチング」は、**恋愛の会話**だけをランダムに並べます。互いに向けて書いたものではありません。

- `land`（恋愛成立）: 告白や「付き合って」に、相手が乗る（好きだよ／わたしも）。
- `hint`（匂わせに乗る）: 彼氏・デートなどの匂わせに、リプライが乗る（彼氏が迎えに来てくれた／それもう付き合ってるじゃん）。

一言の検索は、恋愛の言葉と、ずらして笑える仲間の言葉（ディズニーとUSJ、など）です。ねむい、おやすみなどの日常の一言では探しません。組み合わせは、同じ短い形のまま一語だけ入れ替えるもの（ディズニーシーで迷子／今USJ）を先にします。ふつうの会話（リプライモード）はこれまでどおり別の検索で集めます。
`pairUp` は上の2種類（と、好き・会いたいなどの短い受け答え）だけを `pairs` に書きます。ページはそれ以外を出しません。

検索で投稿を見つけるのは api.fxtwitter.com だけです（vxTwitter と FixupX には検索がありません）。見つけた投稿とリプライは、**vxTwitter（api.vxtwitter.com）と FixupX（fixupx.com）からそれぞれ最大2000件の投稿と2000件のリプライ**を読み、ランダムにふるってから組み合わせます。定期実行は `.github/workflows/collect.yml`（1日3回）です。

- `says`：短い投稿・リプライ（最大2000件）。48時間で消えます。
- `pairs`：上の `says` から作った組み合わせ（最大2000組）。`a` が先、`b` が答え。
- `posts` / `lines`：以前の形式。ページは `pairs` があればそちらを優先します。

（以下、恋愛投稿の検索を有効にしたときの `posts` の説明）

- `posts`：恋愛についての個人の投稿だけ（ジャンルは `romance`）。最大400件。48時間で消えます。
  - 恋愛の言葉で「投稿」を検索し（1回の実行で最大50回、期間はランダムな2時間）、上の3段階のフィルターで選びます。
    「彼女」の話をしている投稿はとても少ないので、検索の半分は彼女側の言葉（`words.json` の `matchShe`）で行います。
  - `side`：その投稿が話している相手。`boyfriend`（彼氏・元カレ）、`girlfriend`（彼女・元カノ。「彼女」が「あの女性」の意味のときは数えません）、
    どちらでもなければ空。**書いた人の性別は判定も表示もしません。** 投稿に書かれた言葉だけを見ます。
  - `wish`：恋人がほしい・できない・いない、という投稿かどうか。
  - `free`：マッチングの対象かどうか。**恋人がいる人の投稿（「彼氏が〜してくれた」など）は対象にしません。**
    対象は、恋人がほしい投稿、元カレ・元カノ・失恋・片思いの投稿、相手を名指ししていない投稿です。
  - 残すもの：書いた人自身の恋愛の話。単独で読める文。
  - 外すもの：相手の募集や「会える人」などの勧誘、DM・LINEへの誘導、ハッシュタグ付き、画像付き、恋愛相談などの商売、
    作品やキャラクター・芸能人・名前を挙げた第三者の話、結婚生活・子ども・浮気の話、体に関する話、性的指向や心の病気の話、学校に関する言葉があるもの。
  - 書いた人のアカウント：作って1年以上、投稿300件以上、フォロワー30〜5万人。プロフィールに勧誘・販売・「サブ垢」などがあるものは外します。
- ページは `free` の投稿だけを使い、次の順で相手を選びます：彼氏側と彼女側の組み合わせ → 同じ話題の言葉がある → どちらも恋人がほしい。
  同じ人どうし、同じ側どうしは組み合わせません。片方の側が足りないときは、相手を名指ししていない投稿が代わりに入ります。
- `lines`：以前のマッチングで使っていた短い反応のリプライ。今のページは使いません。

## 自分で見つけた会話を送る（無料・鍵なし）

自分のXアカウントで普通に検索して見つけた「投稿＋返信」を、このAPIに取り込めます。

1. このリポジトリで新しい Issue を作ります。タイトルは `talk`。
2. 本文に、Xのリンクを1行ずつ書きます。**1行目が投稿、2行目以降が返信**です（返信は最大20件）。
   ```
   https://x.com/投稿した人/status/1234567890
   https://x.com/返信した人/status/1234567999
   ```
3. Submit を押すと、1〜2分で `ingest.mjs` が動いてAPIに入り、Issue は結果のコメント付きで閉じられます。

- 本文は、Xが鍵なしで公開している公式の埋め込みAPI（`publish.x.com/oembed`）で読みます。料金はかかりません。Xにログインしたり、検索を自動で行ったりはしません。
- 読むのは、**このリポジトリの持ち主が作った Issue だけ**です。ほかの人が作った Issue は無視します。
- 返信が複数あるときは、笑いやツッコミのあるものを最大2件選びます。暴力・性的な内容・重い話題・けんか腰の言葉がある投稿は入りません（理由が Issue にコメントされます）。
- ジャンルは、投稿に入っている言葉（`words.json`）から自動で決めます。指定したいときは、本文に `genre: food` のように1行足します。
- 手で送った会話は、14日間APIに残ります（自動で集めた会話は48時間）。

リプライニュースのページからも送れます。`https://githitosh.github.io/reply-news/?owner=1` を一度開くと、
「会話を追加」の欄に「xapiに送る」ボタンが出ます。投稿とリプライのリンクを貼って押すと、上の Issue の画面が内容入りで開きます。

## 自動で集める（`config.json` の `source`）

**今は `fxtwitter` です。** 非公式のサービスに尋ねることをできるだけ減らし、結果を操作されにくくするため、2段階で集めます。

**第1段階：ランダムに検索する**

- api.fxtwitter.com に、リプライの検索を1回の実行で最大50回尋ねます（1回で20件ほど返ります）。非公式のサービスに尋ねるのは、このリプライ検索と、マッチング用の恋愛の投稿の検索（上の「マッチングニュース用のデータ」、最大50回）だけです。1回の実行で合わせて最大100回、1日3回で最大300回です。投稿ごとの返信一覧などは尋ねません。
- 検索語は、ジャンルと関係のない、よく使われる言葉です（`words.json` の `any`：笑、草、なんで、まじ、…）。毎回ランダムに1つ選びます。
- 期間も、直近2日のうちランダムな2時間を毎回選びます。
- リプライ検索では、どのジャンルを集めたいのかは相手には伝わりません。マッチング用の検索だけは恋愛の言葉で検索するので、恋愛の投稿を探していることは相手に伝わります（ランダムな検索では恋愛の投稿がほとんど集まらないためです）。

**第2段階：自分でふるい分ける（このプログラムと、X公式）**

1. 返ってきたリプライを、このプログラムのルール（`rules.mjs`）でふるいます：笑いやツッコミがある、短い、相手が1人、など。
2. 残ったリプライについて、**返信先の投稿と、リプライ自身を、X公式の埋め込みAPI（`publish.x.com`、鍵なし）で読みます。**
   保存するのは、X自身が返した本文と投稿者です。Xで表示されないもの（削除・非公開）は捨てます。
3. X公式から読んだ本文に、もう一度ルールを当てます（個人の投稿か、長さ、安全ルール）。
4. 残った会話を、**本文に入っている言葉でジャンル分けします**（`words.json` の各ジャンルの言葉と `tell`）。どれにも当たらないものは `other` です。

確かめられないのは、「どのリプライが検索結果に出てくるか」と「どの投稿への返信か」の2点です（どちらも第1段階の答えをそのまま使います）。
文面と投稿者は、すべてX公式のものです。

| `source` の値 | 意味 |
|---|---|
| `fxtwitter` | 上の2段階で集めます（無料） |
| `official` | X公式のAPIで、ジャンルの言葉を検索します。Xが発行する鍵（Bearer Token）を、Settings → Secrets and variables → Actions に `X_BEARER_TOKEN` として保存します。返した投稿1件ごとにXの料金がかかるので、1回に読む数に上限（`reads`）があります |
| `auto` | 鍵があれば `official`、なければ集めません |
| `off` | 集めません |

api.fxtwitter.com は、短い時間に多く尋ねると、しばらく検索を断ります。そのため、検索は6秒ずつ間を空け、
断られたら90秒休みます。3回続けて断られたら、そこまでに集めた分で終わります。

### 鍵なしで自分だけでは検索できない理由

api.fxtwitter.com の元になっている公開プログラム（FxEmbed、MITライセンス、https://github.com/FxEmbed/FxEmbed ）を読んで確かめました。
投稿1件を読む処理は鍵もログインも不要ですが、検索・返信の一覧・ユーザーの投稿一覧は、ログイン済みのXアカウントが必須です。
アカウントにログインさせて自動で検索する使い方は、Xの利用規約で禁止されていて、アカウントが凍結されることがあるため、
このリポジトリには入れていません。

## 何を集めるか

- リプライ：第1段階で見つかったリプライのうち、笑いやツッコミがあるもの（日本語は50文字まで）。挨拶や当たりさわりのない返信は選びません。1つの会話にリプライは1件です。
- 最初の投稿：そのリプライの返信先です。X公式から読んだ本文が10〜110文字で、名前に「公式」「ニュース」などが付かないアカウントのもの。
  **返信先が、別の会話の途中の投稿であることもあります**（X公式の埋め込みAPIでは、その投稿が返信かどうか分からないためです）。
- 暴力、性的な内容、重い話題、けんか腰の言葉、広告は、投稿・リプライのどちらにあっても選びません。
- ジャンルは本文の言葉で決めるので、ランダムに集めた会話の多くは `other` になります。

## 応答の形（`v1/talks-ja.json`）

```json
{
  "version": 1,
  "lang": "ja",
  "updated": "2026-11-18T21:04:10Z",
  "source": "official",
  "count": 500,
  "talks": [
    {
      "id": "投稿のID",
      "genre": "food",
      "word": "ラーメン",
      "found": "2026-11-18T21:02:33Z",
      "post": { "id": "…", "handle": "投稿者", "text": "投稿の文", "url": "https://x.com/…/status/…", "at": "投稿の日時" },
      "replies": [ { "id": "…", "handle": "返信者", "text": "リプライの文", "url": "https://x.com/…/status/…" } ]
    }
  ]

```

## 設定（`config.json`）

| 名前 | 初期値 | 意味 |
|---|---|---|
| `source` | `fxtwitter` | 取得元（上の表） |
| `reads` | 300 | `official` のとき、1回の実行で読む投稿の数の上限（料金の上限になります） |
| `langs` | `["ja"]` | 集める言語。英語も集めるなら `["ja", "en"]` |
| `add` | 170 | 1回で集める新しい会話の数 |
| `searches` | 50 | 1回の実行で行うリプライ検索の回数の上限（1回で約20件） |
| `keep` | 500 | APIに残す会話の数 |
| `loveSearches` | 50 | マッチング用に、恋愛の言葉で投稿を検索する回数（1回で約20件） |
| `posts` | 400 | マッチング用に残す投稿の数 |
| `lines` | 300 | マッチング用に残す一言の数 |

## ファイル

| ファイル | 役割 |
|---|---|
| `collect.mjs` | 自動で集めるプログラム（Node 20 以上。追加のインストールは不要） |
| `ingest.mjs` | 手で送った会話（Issue）を取り込むプログラム |
| `rules.mjs` | 選ぶルールと、APIのファイルの書き出し（上の2つが共通で使う） |
| `stats.mjs` | 取り込み量の集計とグラフ（`v1/stats.json`、`v1/intake.svg`、実行のページの表、次の実行の名前） |
| `limit.mjs` | 1つの送り主から依頼が多すぎるときに、しばらく受け付けを止める数え方 |
| `filters.mjs` | 必ず外すもののリスト（残酷なニュース、個人の名誉・私生活にかかわるニュース、誹謗中傷の言葉） |
| `words.json` | 第1段階で検索するランダムな言葉（`any`）と、ジャンル分けに使う言葉 |
| `config.json` | 設定 |
| `.github/workflows/collect.yml` | 1日3回の定期実行と、ブランチ `api` への公開 |
| `.github/workflows/ingest.yml` | Issue が作られたときの取り込みと公開 |

手元で動かす場合：

```bash
node collect.mjs --add 20
```

結果は `public/v1/` にできます。`--dry` を付けると、ファイルを変えずに件数だけ表示します。
