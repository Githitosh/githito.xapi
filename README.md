# githito.xapi

リプライニュース（https://githitosh.github.io/reply-news/ ）のための、**自分専用の「偽検索API」**です。

ページはXを直接検索しません。このリポジトリのプログラムが、あらかじめ1日3回、Xの投稿とリプライを集めて
ファイルに保存しておき、ページはそのファイルを「検索結果」として読みます。検索を待たないので、動画がすぐ作れます。
プログラムもデータもこのリポジトリの中にあり、内容を変えられるのは持ち主だけです。

## APIの入口

ブランチ `api` に置いたファイルが、そのままAPIの応答です（GitHub が配信します。鍵は要りません）。

| 入口 | 内容 |
|---|---|
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/talks-ja.json` | その日の会話すべて（日本語、最大500件） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/search/ja/food.json` | ジャンルごとの会話（`food` の部分がジャンル） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/match-ja.json` | マッチングニュース用：単独で読める投稿（`posts`）と、どの投稿にも合う一言（`lines`） |
| `https://raw.githubusercontent.com/Githitosh/githito.xapi/api/v1/index.json` | 最終更新の時刻と、ジャンルごとの件数 |

ジャンル：`space` `politics` `science` `culture` `local` `entertainment` `safety` `sports` `food`
`restaurant` `romance` `travel`（手で送った会話でどれにも当たらないものは `other`）

## いつ更新されるか

毎日 **6時・12時・18時（日本時間）** に、`.github/workflows/collect.yml` が `collect.mjs` を動かします。
1回の実行で、恋愛の投稿を約1000件、リプライを約1000件（合わせて約2000件）集め、下の3段階のフィルターにかけます。
残った会話は新しいものから500件を残します（48時間たったものは消えます）。
GitHub の都合で、開始が数分〜十数分遅れることがあります。
Actions タブ →「Collect」→ Run workflow で、すぐ1回動かすこともできます。
そのとき `rejudge` にチェックを入れると、検索は一切せず、保存済みのデータを今のルールで判定し直すだけの実行になります
（ルールを直したあと、すぐAPIから外したいときに使います。30秒ほどで終わります）。

## 3段階のフィルター

集めた約2000件は、次の順にふるいにかけます。各段階を何件が通ったかは、実行のログと `index.json` の `stages`（`match-ja.json` にも同じもの）に残ります。

| 段階 | 何を見るか |
|---|---|
| 集める | 検索で返ってきた投稿・リプライ（1回の検索で20件ほど。投稿50回＋リプライ50回） |
| フィルター1：出してよいか・誰のアカウントか | 暴力・性的な内容・重い話題・けんか腰・広告・勧誘・体に関する話・学校に関する言葉を外す。投稿は、作って1年以上・投稿300件以上・フォロワー30〜5万人のアカウントだけ。プロフィールに勧誘や販売があるもの、鍵付き、未成年と分かるものは外す |
| フィルター2：内容が合っているか | 投稿は「単独で読める、本人の恋愛の話」だけ（作品・キャラクター・芸能人・結婚生活・説教調は外す）。リプライは「ツッコミや笑いのある返信」か「数文字の反応」だけ |
| フィルター3：X公式で読み直して再判定 | 通ったものを X公式の埋め込みAPIで読み直し、X の本文でフィルター1・2をもう一度かける。リプライは、返信先の投稿も読んで判定する。X で表示されないものは捨てる |

このあとページ側で、組み合わせるときにもう一度選びます（別の人どうし、本当の返信ペアではない、リプライが触れている言葉が投稿にある）。

## マッチングニュース用のデータ（`match-ja.json`）

ページの「マッチング」は、**恋愛の会話**だけをランダムに並べます。互いに向けて書いたものではありません。

- `land`（恋愛成立）: 告白や「付き合って」に、相手が乗る（好きだよ／わたしも）。
- `hint`（匂わせに乗る）: 彼氏・デートなどの匂わせに、リプライが乗る（彼氏が迎えに来てくれた／それもう付き合ってるじゃん）。

一言の検索は、恋愛の言葉と、ずらして笑える仲間の言葉（ディズニーとUSJ、など）です。ねむい、おやすみなどの日常の一言では探しません。組み合わせは、同じ短い形のまま一語だけ入れ替えるもの（ディズニーシーで迷子／今USJ）を先にします。ふつうの会話（リプライモード）はこれまでどおり別の検索で集めます。
`pairUp` は上の2種類（と、好き・会いたいなどの短い受け答え）だけを `pairs` に書きます。ページはそれ以外を出しません。

検索で投稿を見つけるのは api.fxtwitter.com だけです（vxTwitter と FixupX には検索がありません）。見つけた投稿とリプライは、**vxTwitter（api.vxtwitter.com）と FixupX（fixupx.com）からそれぞれ最大2000件の投稿と2000件のリプライ**を読み、ランダムにふるってから組み合わせます。定期実行は `.github/workflows/collect.yml`（1日3回）です。

- `says`：短い投稿・リプライ（最大2000件）。48時間で消えます。
- `pairs`：上の `says` から作った組み合わせ（最大2000組）。`a` が先、`b` が答え。
- `posts` / `lines`：以前の形式。ページは `pairs` があればそちらを優先します。

（以下、恋愛投稿の検索を有効にしたときの `posts` の説明）

- `posts`：恋愛についての個人の投稿だけ（ジャンルは `romance`）。最大400件。48時間で消えます。
  - 恋愛の言葉で「投稿」を検索し（1回の実行で最大50回、期間はランダムな2時間）、上の3段階のフィルターで選びます。
    「彼女」の話をしている投稿はとても少ないので、検索の半分は彼女側の言葉（`words.json` の `matchShe`）で行います。
  - `side`：その投稿が話している相手。`boyfriend`（彼氏・元カレ）、`girlfriend`（彼女・元カノ。「彼女」が「あの女性」の意味のときは数えません）、
    どちらでもなければ空。**書いた人の性別は判定も表示もしません。** 投稿に書かれた言葉だけを見ます。
  - `wish`：恋人がほしい・できない・いない、という投稿かどうか。
  - `free`：マッチングの対象かどうか。**恋人がいる人の投稿（「彼氏が〜してくれた」など）は対象にしません。**
    対象は、恋人がほしい投稿、元カレ・元カノ・失恋・片思いの投稿、相手を名指ししていない投稿です。
  - 残すもの：書いた人自身の恋愛の話。単独で読める文。
  - 外すもの：相手の募集や「会える人」などの勧誘、DM・LINEへの誘導、ハッシュタグ付き、画像付き、恋愛相談などの商売、
    作品やキャラクター・芸能人・名前を挙げた第三者の話、結婚生活・子ども・浮気の話、体に関する話、性的指向や心の病気の話、学校に関する言葉があるもの。
  - 書いた人のアカウント：作って1年以上、投稿300件以上、フォロワー30〜5万人。プロフィールに勧誘・販売・「サブ垢」などがあるものは外します。
- ページは `free` の投稿だけを使い、次の順で相手を選びます：彼氏側と彼女側の組み合わせ → 同じ話題の言葉がある → どちらも恋人がほしい。
  同じ人どうし、同じ側どうしは組み合わせません。片方の側が足りないときは、相手を名指ししていない投稿が代わりに入ります。
- `lines`：以前のマッチングで使っていた短い反応のリプライ。今のページは使いません。

## 自分で見つけた会話を送る（無料・鍵なし）

自分のXアカウントで普通に検索して見つけた「投稿＋返信」を、このAPIに取り込めます。

1. このリポジトリで新しい Issue を作ります。タイトルは `talk`。
2. 本文に、Xのリンクを1行ずつ書きます。**1行目が投稿、2行目以降が返信**です（返信は最大20件）。
   ```
   https://x.com/投稿した人/status/1234567890
   https://x.com/返信した人/status/1234567999
   ```
3. Submit を押すと、1〜2分で `ingest.mjs` が動いてAPIに入り、Issue は結果のコメント付きで閉じられます。

- 本文は、Xが鍵なしで公開している公式の埋め込みAPI（`publish.x.com/oembed`）で読みます。料金はかかりません。Xにログインしたり、検索を自動で行ったりはしません。
- 読むのは、**このリポジトリの持ち主が作った Issue だけ**です。ほかの人が作った Issue は無視します。
- 返信が複数あるときは、笑いやツッコミのあるものを最大2件選びます。暴力・性的な内容・重い話題・けんか腰の言葉がある投稿は入りません（理由が Issue にコメントされます）。
- ジャンルは、投稿に入っている言葉（`words.json`）から自動で決めます。指定したいときは、本文に `genre: food` のように1行足します。
- 手で送った会話は、14日間APIに残ります（自動で集めた会話は48時間）。

リプライニュースのページからも送れます。`https://githitosh.github.io/reply-news/?owner=1` を一度開くと、
「会話を追加」の欄に「xapiに送る」ボタンが出ます。投稿とリプライのリンクを貼って押すと、上の Issue の画面が内容入りで開きます。

## 自動で集める（`config.json` の `source`）

**今は `fxtwitter` です。** 非公式のサービスに尋ねることをできるだけ減らし、結果を操作されにくくするため、2段階で集めます。

**第1段階：ランダムに検索する**

- api.fxtwitter.com に、リプライの検索を1回の実行で最大50回尋ねます（1回で20件ほど返ります）。非公式のサービスに尋ねるのは、このリプライ検索と、マッチング用の恋愛の投稿の検索（上の「マッチングニュース用のデータ」、最大50回）だけです。1回の実行で合わせて最大100回、1日3回で最大300回です。投稿ごとの返信一覧などは尋ねません。
- 検索語は、ジャンルと関係のない、よく使われる言葉です（`words.json` の `any`：笑、草、なんで、まじ、…）。毎回ランダムに1つ選びます。
- 期間も、直近2日のうちランダムな2時間を毎回選びます。
- リプライ検索では、どのジャンルを集めたいのかは相手には伝わりません。マッチング用の検索だけは恋愛の言葉で検索するので、恋愛の投稿を探していることは相手に伝わります（ランダムな検索では恋愛の投稿がほとんど集まらないためです）。

**第2段階：自分でふるい分ける（このプログラムと、X公式）**

1. 返ってきたリプライを、このプログラムのルール（`rules.mjs`）でふるいます：笑いやツッコミがある、短い、相手が1人、など。
2. 残ったリプライについて、**返信先の投稿と、リプライ自身を、X公式の埋め込みAPI（`publish.x.com`、鍵なし）で読みます。**
   保存するのは、X自身が返した本文と投稿者です。Xで表示されないもの（削除・非公開）は捨てます。
3. X公式から読んだ本文に、もう一度ルールを当てます（個人の投稿か、長さ、安全ルール）。
4. 残った会話を、**本文に入っている言葉でジャンル分けします**（`words.json` の各ジャンルの言葉と `tell`）。どれにも当たらないものは `other` です。

確かめられないのは、「どのリプライが検索結果に出てくるか」と「どの投稿への返信か」の2点です（どちらも第1段階の答えをそのまま使います）。
文面と投稿者は、すべてX公式のものです。

| `source` の値 | 意味 |
|---|---|
| `fxtwitter` | 上の2段階で集めます（無料） |
| `official` | X公式のAPIで、ジャンルの言葉を検索します。Xが発行する鍵（Bearer Token）を、Settings → Secrets and variables → Actions に `X_BEARER_TOKEN` として保存します。返した投稿1件ごとにXの料金がかかるので、1回に読む数に上限（`reads`）があります |
| `auto` | 鍵があれば `official`、なければ集めません |
| `off` | 集めません |

api.fxtwitter.com は、短い時間に多く尋ねると、しばらく検索を断ります。そのため、検索は6秒ずつ間を空け、
断られたら90秒休みます。3回続けて断られたら、そこまでに集めた分で終わります。

### 鍵なしで自分だけでは検索できない理由

api.fxtwitter.com の元になっている公開プログラム（FxEmbed、MITライセンス、https://github.com/FxEmbed/FxEmbed ）を読んで確かめました。
投稿1件を読む処理は鍵もログインも不要ですが、検索・返信の一覧・ユーザーの投稿一覧は、ログイン済みのXアカウントが必須です。
アカウントにログインさせて自動で検索する使い方は、Xの利用規約で禁止されていて、アカウントが凍結されることがあるため、
このリポジトリには入れていません。

## 何を集めるか

- リプライ：第1段階で見つかったリプライのうち、笑いやツッコミがあるもの（日本語は50文字まで）。挨拶や当たりさわりのない返信は選びません。1つの会話にリプライは1件です。
- 最初の投稿：そのリプライの返信先です。X公式から読んだ本文が10〜110文字で、名前に「公式」「ニュース」などが付かないアカウントのもの。
  **返信先が、別の会話の途中の投稿であることもあります**（X公式の埋め込みAPIでは、その投稿が返信かどうか分からないためです）。
- 暴力、性的な内容、重い話題、けんか腰の言葉、広告は、投稿・リプライのどちらにあっても選びません。
- ジャンルは本文の言葉で決めるので、ランダムに集めた会話の多くは `other` になります。

## 応答の形（`v1/talks-ja.json`）

```json
{
  "version": 1,
  "lang": "ja",
  "updated": "2026-11-18T21:04:10Z",
  "source": "official",
  "count": 500,
  "talks": [
    {
      "id": "投稿のID",
      "genre": "food",
      "word": "ラーメン",
      "found": "2026-11-18T21:02:33Z",
      "post": { "id": "…", "handle": "投稿者", "text": "投稿の文", "url": "https://x.com/…/status/…", "at": "投稿の日時" },
      "replies": [ { "id": "…", "handle": "返信者", "text": "リプライの文", "url": "https://x.com/…/status/…" } ]
    }
  ]
}
```

## 設定（`config.json`）

| 名前 | 初期値 | 意味 |
|---|---|---|
| `source` | `fxtwitter` | 取得元（上の表） |
| `reads` | 300 | `official` のとき、1回の実行で読む投稿の数の上限（料金の上限になります） |
| `langs` | `["ja"]` | 集める言語。英語も集めるなら `["ja", "en"]` |
| `add` | 170 | 1回で集める新しい会話の数 |
| `searches` | 50 | 1回の実行で行うリプライ検索の回数の上限（1回で約20件） |
| `keep` | 500 | APIに残す会話の数 |
| `loveSearches` | 50 | マッチング用に、恋愛の言葉で投稿を検索する回数（1回で約20件） |
| `posts` | 400 | マッチング用に残す投稿の数 |
| `lines` | 300 | マッチング用に残す一言の数 |

## ファイル

| ファイル | 役割 |
|---|---|
| `collect.mjs` | 自動で集めるプログラム（Node 20 以上。追加のインストールは不要） |
| `ingest.mjs` | 手で送った会話（Issue）を取り込むプログラム |
| `rules.mjs` | 選ぶルールと、APIのファイルの書き出し（上の2つが共通で使う） |
| `words.json` | 第1段階で検索するランダムな言葉（`any`）と、ジャンル分けに使う言葉 |
| `config.json` | 設定 |
| `.github/workflows/collect.yml` | 1日3回の定期実行と、ブランチ `api` への公開 |
| `.github/workflows/ingest.yml` | Issue が作られたときの取り込みと公開 |

手元で動かす場合：

```bash
node collect.mjs --add 20
```

結果は `public/v1/` にできます。`--dry` を付けると、ファイルを変えずに件数だけ表示します。
